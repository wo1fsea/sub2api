## 8. LOCAL_UPGRADE 本地热升级顺序

### 8.1 先适配工具，再接触生产

当前 `upgrade-current.mjs` 明确只接受 `0.2.13`，并存在旧默认版本；不能直接拿 0.2.19 manifest 执行，也不能简单去掉版本检查。审查升级、恢复、预检和演练脚本的版本、路径、迁移数、业务投影及背景角色假设，改为经过测试的 0.2.13 → 0.2.19 路径，仍严格校验 manifest、源 SHA、镜像、架构、配置和快照。

现有线上目录名 `current-0.2.13` 是实际部署路径，不因版本提升自动重命名。保持恢复工作区可用；新工作区构建和工具执行需核对其路径推导，避免把新候选误当成旧部署。演练成功/失败、prepare-failed 重试、activate 中断和 rollback 都应有针对性测试。

### 8.2 包与预检

只打包 Linux ARM64，固定构建输入并绑定最终源码；执行准确镜像的空库 smoke、旧静态资源桥接和必要代理协议演练。核验存储空间、端口 `18585` 空闲、构建资源上限、线上响应、备份时间窗、后台任务/备份恢复操作、Redis 兼容和当前回滚镜像。保留旧资源上限保护，达到上限先盘点容量，不静默删除仍被浏览器使用的文件。

### 8.3 backup → rehearse → prepare:18585 → activate

以下命令是后续执行模板，必须在已适配且验证过的源码工作区使用；`MANIFEST`、`BACKUP`、`RESTORE_REPORT` 要替换为本次产物的绝对路径，不能原样复制占位词运行。

```sh
SUB2API_BACKUP_APP=sub2api-current-app node deploy/local-upgrade/backup-private.mjs /Users/clawbotbot/Projects/sub2api-upgrade-private
node deploy/local-upgrade/rehearse-private.mjs BACKUP MANIFEST
node deploy/local-upgrade/upgrade-current.mjs prepare MANIFEST BACKUP RESTORE_REPORT
node deploy/local-upgrade/upgrade-current.mjs activate MANIFEST
node deploy/local-upgrade/upgrade-current.mjs status MANIFEST
```

1. **Backup**：先确认 `sub2api-current-app` 确为现场容器。备份 PostgreSQL、必要 Redis 状态、应用数据、私有配置和加密材料；目录 0700、文件 0600，存放 Git 之外，不打印 `recovery-private.json`。校验备份完整性和可恢复性。
2. **Rehearse**：针对同一个最终 manifest 恢复并执行第 5 节全部迁移验收，生成独立、通过的恢复报告。报告绑定备份和候选镜像；过期备份或镜像变化必须重新备份/演练，不能手改通过标记。
3. **Prepare**：仅在迁移、业务策略和回滚兼容门槛通过后启动 `127.0.0.1:18585` 候选。使用独立应用卷、既有生产 PostgreSQL/Redis，禁用重复后台角色，保持原入口。此时启动即可执行共享库迁移，必须监测旧站而不是等到 activate 才检查风险。
4. **候选验证**：核对版本/源 SHA/镜像、身份认证和现有会话、站点外观、额度 API/编译资源、旧标签页静态资源、当前 Codex 模型及 Terra 的真实短流；按预算验证 Gemini/Antigravity 生图和账本。出现数据差异、策略越权、真实调用失败或资源压力就停在原入口。
5. **Activate**：按当前工具将稳定入口交给候选，候选承接流量期间仅替换 canonical 应用为固定新镜像，并恢复原后台角色；验证 canonical 后再按工具流程路由回去。保持 `18080`、`18480`、tailnet HTTPS 和其他 Serve 端口的既有访问契约，不重建数据库、Redis 或整个 Compose 项目。
6. **复验**：通过原稳定入口再次核验真实流、模型、登录、额度、生图、计费和后台单实例；核对运行路由、持久化路由、私有 Compose/state 与 manifest 校验和一致，确保恢复启动新版本。记录观察窗口内错误率、延迟、资源和迁移锁情况。
7. **收尾**：保留旧镜像、旧配置、包、备份及可回滚证据，不自动清理旧资源。当前 LOCAL_UPGRADE 允许切换时客户端重连，但不承诺无损续流，不盲目重放 POST。只有实际验证支持时才能宣称无停机；超时和中断如实记录。

| 老脚本版本锁与路径假设 | 适配并测试，不绕过校验；恢复路径、镜像和状态不一致即停止 |
| 共享库迁移影响旧站 | prepare 期间持续探测，限制锁等待并记录实际耗时；流量未切换不等于数据未变 |
| 角色重复、缓存或会话不兼容 | 候选关闭重复任务，核验单一后台所有者及旧调度兼容；实际状态异常不切流 |
| Terra 目录可见但实际不可用 | 真实 Responses、模型身份和账本验收；无权限/上游故障明确为未通过 |
| 旧标签页资源丢失或构建挤占线上资源 | 保留指纹资源、遵守容量上限、串行重任务；线上响应受影响时停止本次自有重任务 |
| 切换中断或持久化配置漂移 | 使用当前工具的状态/恢复流程，先核对快照；不得手工拼接历史脚本继续执行 |

热回滚绝不把升级前数据库快照覆盖回线上，否则会丢失升级后的写入；不执行整项目 `compose down`。数据库灾难恢复是独立流程，需要明确的数据损失范围和授权。迁移 246 的开关回退只允许依据记录做针对性配置恢复，不能盲目把全部分组设为 false。旧镜像无法安全回退时报告阻断并采用前向修复方案，不能冒充成功回滚。
